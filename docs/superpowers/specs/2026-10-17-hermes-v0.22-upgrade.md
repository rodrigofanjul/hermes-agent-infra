# Upgrade a hermes-agent v0.22.2 + hermes-webui v0.52.458 (2026-10-17)

## Contexto

Producción corría `hermes-agent` 0.21.0 en el volumen `hermes-agent-src`: el
bump a `v2026.9.24` (commit b765644) nunca se aplicó porque ese volumen no se
recreó (ver README sección 11, paso 4). Se aprovechó para saltar directo a las
últimas estables: agente `v0.22.2` (Docker Hub: `stable`/`latest`) y webui
`v0.52.458` (primer track estable que incluye el fix #6458).

## Qué cambia en v0.22 y cómo se resolvió

| Cambio upstream | Efecto | Solución |
|---|---|---|
| Tags SemVer (`v0.22.x`) en vez de `vYYYY.M.D`; los parches `0.21.x` no tienen imagen | No hay punto intermedio | `FROM nousresearch/hermes-agent:v0.22.2` |
| Python 3.14, venv sin `pip`, `uv` fuera del PATH (`/opt/hermes/tools/uv-*/uv`) | `uv pip install` del Dockerfile viejo falla (exit 127) | El Dockerfile ubica el `uv` con `find` |
| `PLAYWRIGHT_BROWSERS_PATH=/opt/hermes/tools` y Chromium propio horneado ahí | `playwright install` en esa carpeta **borra** el Chromium de Hermes (warning de stage2) | `ENV PLAYWRIGHT_BROWSERS_PATH=/opt/hermes/.playwright` antes de instalar el nuestro (mismo esquema que antes; `AGENT_BROWSER_EXECUTABLE_PATH` sigue valiendo) |
| Mnemosyne pasa a plugin de catálogo (`hermes plugins install mnemosyne`), con su propio entorno bajo `/opt/data/installs` | El `pip install mnemosyne-hermes==0.5.0` y los symlinks de `plugins/mnemosyne` ya no aplican | `mnemosyne-bootstrap.sh` mueve los symlinks viejos, instala el plugin en el primer arranque y reinicia el gateway |
| `mnemosyne-hermes` 0.7.3/0.7.4 no construye `MnemosyneMemoryProvider()` con Hermes 0.22 ("no binding for the current home") | Memoria larga no disponible | `mnemosyne-ctor-fix.py` aplica el PR upstream #1155 solo si el constructor falla (ver abajo) |
| `tools/.install.lock` queda `root:root 0600` en la imagen | `hermes-webui` sale con `rsync ... Permission denied` (pasa con 0.52.379 y 0.52.458) | `RUN find /opt/hermes -type f ! -perm -o+r -exec chmod a+r {} +` |
| Gateway bajo s6 (`main-hermes`) arranca en paralelo al bootstrap | Puede cargar el plugin antes de instalarlo/parcharlo | El bootstrap hace `hermes gateway restart` solo si instaló/parcheó en ese arranque |

## `mnemosyne-ctor-fix.py` (parche temporal)

Upstream (mnemosyne-oss/mnemosyne): issues #1114, #1143, #1178; fix en `main`
(PR #1155, 2026-10-11) pero **sin release en PyPI al 2026-10-17** (0.7.5 no
existe). El script aplica exactamente los dos reemplazos de ese PR, solo si el
constructor falla, y revierte si el archivo parcheado sigue sin construir. Una
vez que salga una versión corregida, el probe pasa y el script no hace nada:
puede quitarse en el siguiente bump de Mnemosyne. No se usó el atajo de
pre-sembrar el home actual porque los mantenedores lo desaconsejan (debilita el
fail-closed por home).

La memoria vive en `/opt/data/mnemosyne/data/mnemosyne.db` (volumen
`hermes-data`); el bootstrap nunca la toca. La nueva versión agrega tablas
(`media_assets`, `media_moments`) y consolida el WAL, sin perder filas.

## Seguimiento posterior al corte (2026-10-18)

- **hermes-webui no podía importar el agente** (`AIAgent not available ... No module named 'dotenv'`): la imagen de la webui crea su venv en Python 3.12 y el `pyproject.toml` del agente (desde v0.21.6) condiciona sus dependencias centrales a `python_version >= '3.14'`. Workaround upstream (nesquena/hermes-webui#8113, abierto): `UV_PYTHON=3.14` en el servicio de la webui. El ensayo previo solo había comprobado `/health`, no el import del agente.
- **Mnemosyne en la webui:** nunca se había activado ahí (el plugin se importa desde un entorno bajo `/opt/data/installs` que solo ven los procesos del agente). Se resolvió con un `sitecustomize.py` que escribe `mnemosyne-bootstrap.sh` en `hermes-data/webui-site/` y `PYTHONPATH` en el servicio de la webui. Se agrega el entorno del plugin al **final** del `sys.path` (los paquetes de la webui conservan prioridad) y solo si coincide la versión de Python. Probado antes de publicar: sin la variable el import falla; con ella importa y el proveedor construye; el bloque del bootstrap es idempotente (segunda corrida no reescribe).
- **Cron `Sync movimientos tarjetas -> Sheet gastos`:** su entrega era `origin` y resolvía a la plataforma `webui` (`unknown platform 'webui'`), por lo que los avisos de fallo no llegaban. Cambiado a `whatsapp` con `hermes cron edit` (copia previa de `cron/jobs.json` en `hermes-data`).
- **Google OAuth:** el token estaba vencido o revocado cuando corrieron los syncs de la madrugada del 18/10 (antes del corte). Si la app de Google Cloud está en modo "Testing", los tokens caducan a los 7 días; pasarla a "Producción" lo evita.

- **Herramienta de navegador de Hermes (`browser_exec`) sin CLI:** Hermes respondía que no tenía navegador (p. ej. al pedirle buscar empleo). Causa: desde v0.22 el CLI `agent-browser` lo gestiona `hermes pm` y el chequeo de disponibilidad nunca lo instala (`pm doctor`: `agent-browser: not installed`), así que el modelo no llega a usarlo. No era una regresión de la actualización: los logs del 8/10 ya mostraban el mismo aviso. En este modo (`browser_use_cli_mode`) las herramientas sueltas `browser_*` se ocultan a propósito y la única es `browser_exec`. Solución: `hermes pm install agent-browser` en `mnemosyne-bootstrap.sh` (queda en `hermes-data/tools`, no-op de ~2 s si ya está). Probado: `agent-browser open https://example.com` + `snapshot` con el Chromium de Playwright.

- **Navegador en los chats de la webui:** la webui ejecuta las herramientas (terminal, navegador) en su propio contenedor (Debian 13, aarch64), que no traía las 24 librerías compartidas que necesita Chromium (`ldd` -> `not found`) y no tenía `AGENT_BROWSER_EXECUTABLE_PATH`. Solución reproducible: `Dockerfile.webui` (FROM la imagen oficial + `apt-get install` de esas librerías, nombres de Debian 13 con sufijo `t64`) y la variable en el compose apuntando al Chromium de Playwright del volumen `hermes-agent-src` (montado de solo lectura en la webui). Probado antes de publicar: instalación manual de los paquetes en el contenedor vivo + `agent-browser open https://example.com` como usuario `hermeswebui` (OK), y build de `Dockerfile.webui` en el servidor (exit 0, `curl` y arranque heredados).
