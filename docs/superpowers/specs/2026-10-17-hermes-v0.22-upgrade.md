# Upgrade a hermes-agent v0.22.2 + hermes-webui v0.52.458 (2026-10-17)

## Contexto

Producción corría `hermes-agent` 0.21.0 en el volumen `hermes-agent-src`: el
bump a `v2026.9.24` (commit b765644) nunca se aplicó porque ese volumen no se
recreó (ver README sección 11, paso 4). Se aprovechó para saltar directo a las
últimas estables: agente `v0.22.2` (Docker Hub: `stable`/`latest`) y webui
`v0.52.458` (primer track estable que incluye el fix #6458).

## Qué cambia en v0.22 y cómo se resolvió

| Cambio upstream | Efecto | Solución |
|---|---|---|
| Tags SemVer (`v0.22.x`) en vez de `vYYYY.M.D`; los parches `0.21.x` no tienen imagen | No hay punto intermedio | `FROM nousresearch/hermes-agent:v0.22.2` |
| Python 3.14, venv sin `pip`, `uv` fuera del PATH (`/opt/hermes/tools/uv-*/uv`) | `uv pip install` del Dockerfile viejo falla (exit 127) | El Dockerfile ubica el `uv` con `find` |
| `PLAYWRIGHT_BROWSERS_PATH=/opt/hermes/tools` y Chromium propio horneado ahí | `playwright install` en esa carpeta **borra** el Chromium de Hermes (warning de stage2) | `ENV PLAYWRIGHT_BROWSERS_PATH=/opt/hermes/.playwright` antes de instalar el nuestro (mismo esquema que antes; `AGENT_BROWSER_EXECUTABLE_PATH` sigue valiendo) |
| Mnemosyne pasa a plugin de catálogo (`hermes plugins install mnemosyne`), con su propio entorno bajo `/opt/data/installs` | El `pip install mnemosyne-hermes==0.5.0` y los symlinks de `plugins/mnemosyne` ya no aplican | `mnemosyne-bootstrap.sh` mueve los symlinks viejos, instala el plugin en el primer arranque y reinicia el gateway |
| `mnemosyne-hermes` 0.7.3/0.7.4 no construye `MnemosyneMemoryProvider()` con Hermes 0.22 ("no binding for the current home") | Memoria larga no disponible | `mnemosyne-ctor-fix.py` aplica el PR upstream #1155 solo si el constructor falla (ver abajo) |
| `tools/.install.lock` queda `root:root 0600` en la imagen | `hermes-webui` sale con `rsync ... Permission denied` (pasa con 0.52.379 y 0.52.458) | `RUN find /opt/hermes -type f ! -perm -o+r -exec chmod a+r {} +` |
| Gateway bajo s6 (`main-hermes`) arranca en paralelo al bootstrap | Puede cargar el plugin antes de instalarlo/parcharlo | El bootstrap hace `hermes gateway restart` solo si instaló/parcheó en ese arranque |

## `mnemosyne-ctor-fix.py` (parche temporal)

Upstream (mnemosyne-oss/mnemosyne): issues #1114, #1143, #1178; fix en `main`
(PR #1155, 2026-10-11) pero **sin release en PyPI al 2026-10-17** (0.7.5 no
existe). El script aplica exactamente los dos reemplazos de ese PR, solo si el
constructor falla, y revierte si el archivo parcheado sigue sin construir. Una
vez que salga una versión corregida, el probe pasa y el script no hace nada:
puede quitarse en el siguiente bump de Mnemosyne. No se usó el atajo de
pre-sembrar el home actual porque los mantenedores lo desaconsejan (debilita el
fail-closed por home).

La memoria vive en `/opt/data/mnemosyne/data/mnemosyne.db` (volumen
`hermes-data`); el bootstrap nunca la toca. La nueva versión agrega tablas
(`media_assets`, `media_moments`) y consolida el WAL, sin perder filas.
